# T80コア内部に残っていた潜在バグ（Phase11〜12での発見と修正）

更新日: 2026-10-11

## 背景

Phase1〜10までの24bit拡張は、すべて「既存のZ80命令が1命令あたり最大6
マシンサイクル（`MCycle`、3bit幅、表現できる値は1〜7）しか使わない」
という、本プロジェクトが触れていなかった**T80コア（Daniel Wallner氏の
オリジナル実装）自体の既存の暗黙の前提**の上に成り立っていた。

Phase11でCALL.L（ED CD、M2専用24bit far call）を実装する際、初めて
「1命令でMCycleが7（"111"）に到達する」設計が必要になり、この暗黙の
前提が崩れて複数の潜在バグが一度に表面化した。これらはいずれも
**本プロジェクトが24bit拡張として追加した機能のバグではなく、
オリジナルのT80コアに元から存在していた設計上の制約**である。

本ドキュメントは、発見された問題・根本原因・修正内容を記録し、
Phase13以降で同種の制約に再度ぶつかった際にすぐ参照できるようにする
ことを目的とする。

## 根本原因：`MCycle=110/111`の二重の意味

T80コアは、DD/FD（IX/IY）プレフィックス付きでさらにCBプレフィックスが
続く命令（例: `LD (IX+d),r` のビット操作系）のために、「実効アドレス
計算用にdisplacementバイトを読み直す」特殊な2段階フェッチの仕組みを
持っている。これは次のように動作する。

1. 通常の命令実行中に`NextIs_XY_Fetch`（`XY_State/="00"`、すなわち
   DD/FDプレフィックス実行中であることが必須条件）が成立すると、
   現在の`MCycle`を`Pre_XY_F_M`へ退避し、`MCycle`を強制的に
   `"110"`（6）へジャンプさせる。
2. その特殊な1サイクル（displacementバイトの再読込等）が終わると、
   `MCycle`は通常通り`"111"`（7）へインクリメントされる。
3. **ここで、`MCycle="111"`に到達したこと自体をトリガーとして、
   無条件に`Pre_XY_F_M+1`へ復帰する処理が、T80コアのメイン状態機械
   (`t80.vhd`)に実装されている**。

この3番目の挙動が問題だった。「`MCycle`が7に達したら無条件に復帰処理
を行う」という判定は、**本来その直前にDD/FD+CBの特殊フェッチを
経由してきたかどうかを一切確認していない**。これまでのZ80命令は
すべて6サイクル以内（`MCycle`が7に到達しない）に収まっていたため、
この判定が「常に安全」に見えていただけで、実際には「`MCycle`の値
だけを見て判断する」という脆い前提の上に成り立っていた。

CALL.L（7サイクル命令）を追加した瞬間、この前提が崩れ、CALL.L自身の
7サイクル目（`MCycle="111"`）が、DD/FD+CBとは無関係にこの復帰処理を
誤発火させ、CPUの状態（`MCycle`カウンタ自体を含む）が破壊される、
という形で問題が表面化した。

同種の「`MCycle=110`または`111`という値だけを見て、DD/FD+CB専用の
処理を無条件に行ってしまう」コードが、調査の結果**t80.vhd・
t80_mcode.vhdの合計5箇所**に見つかった。

## 発見された5箇所の潜在バグ

いずれも「`XY_State /= "00"`（現在DD/FDプレフィックスを実行中である
こと）」という条件を追加でガードすることで、DD/FD+CB自体の動作を
一切変更せずに修正した。

### 1. `t80.vhd` メイン状態機械（最重要・直接の原因）

```vhdl
-- 修正前
elsif (MCycle = "111") or
    (MCycle = "110" and Mode = 1 and ISet /= "01") then
    MCycle <= std_logic_vector(unsigned(Pre_XY_F_M) + 1);
```

`MCycle="111"`に達したら、DD/FD+CBの特殊フェッチを経由したかどうかに
関わらず無条件に`Pre_XY_F_M`から復帰する。CALL.L実行中（DD/FDとは
無関係）に`MCycle`が7に達すると、この分岐が誤って発火し、
`Pre_XY_F_M`（通常は`"000"`のまま、または無関係な値）から
`MCycle`が再設定され、以降の命令実行が完全に破綻する。

**修正**: 新規1bitフラグ`XYF_Pending`を追加。`NextIs_XY_Fetch`経由で
`MCycle<="110"`へジャンプする、まさにその瞬間にのみ`XYF_Pending<='1'`
をセットし、この復帰判定を`(MCycle="111" and XYF_Pending='1')`に限定
した（消費したら`XYF_Pending<='0'`に戻す）。`MCycle`自体の幅（3bit）
は変更していない。

### 2. `t80_mcode.vhd` 末尾の共通ブロック

```vhdl
-- 修正前
if Mode < 2 then
    if MCycle = "110" then
        Inc_PC <= '1';
        ...
    end if;
    if MCycle = "111" then
        ...
        Set_BusB_To(2 downto 0) <= SSS;
        ...
        if IRB = "00110110" or ISet = "01" then
            Inc_PC <= '1';
        else
            NoRead <= '1';
        end if;
    end if;
end if;
```

命令の種類（`ISet`/`IRB`）に関わらず、`MCycle`が110/111であれば
`Inc_PC`・`Set_Addr_To`・`TStates`・`Set_BusB_To`・`NoRead`を無条件に
上書きする。CALL.Lの6・7サイクル目（独自のpush frame書き込み処理中）
でこれが発火し、`Inc_PC`が意図せず`'1'`になる、`NoRead`が誤って立つ、
といった形で該当サイクルの動作を破壊していた。

**修正**: 両方の`if`文に`and XY_State /= "00"`を追加。

### 3. `t80.vhd` (IX/IY+d)実効アドレス計算

```vhdl
-- 修正前
if TState = 3 and MCycle = "110" then
    TmpAddr <= std_logic_vector(signed(RegBusC) + signed(DI_Reg));
    ...
end if;
```

CALL.Lが`TmpAddr`/`TmpBank`に24bitターゲットアドレスをラッチして
保持している最中（6サイクル目）に、この(IX+d)用の実効アドレス計算が
無条件発火し、`TmpAddr`/`TmpBank`を無関係な値（`RegBusC`+`DI_Reg`の
計算結果）で上書きしてしまっていた。CALL.Lのジャンプ先が破壊される、
という形で最も直接的に影響した箇所。

**修正**: `and XY_State /= "00"`を追加。

### 4. `t80.vhd` `XY_Ind`セット

```vhdl
-- 修正前
if MCycle = "110" then
    XY_Ind <= '1';
    if Prefix = "01" then
        ISet <= "01";
    end if;
end if;
```

**修正**: `and XY_State /= "00"`を追加（`XY_Ind`が意図せず`'1'`に
なると、以降DD/FDプレフィックス絡みの判定に影響が残る可能性がある
ため、念のため修正）。

### 5. `t80.vhd` `RegAddrC`選択

```vhdl
-- 修正前
if ((JumpXY = '1' or LDSPHL = '1') and XY_State /= "00") or (MCycle = "110") then
    RegAddrC <= XY_State(1) & "11";
end if;
```

**修正**: 2つ目の条件にも`and XY_State /= "00"`を追加。

## CALL.L cc自身の実装バグ（T80コア本体とは別、Phase11新規コードのバグ）

上記5箇所の修正とは別に、**Phase11で新規に書いたCALL.L cc自身のコード**
にもバグがあった。条件不成立（callされない）場合でも、push phase直前の
「最初のMSP24デクリメント」だけは発火してしまい、対応する書き込みが
一切ないままMSP24がずれる、という問題だった。

条件分岐（成立/不成立）はM4（最後のfetchサイクル）のmcode内部で
行われるが、decrementのトリガー条件（t80.vhdの直接IR一致ブロック）が
`IR`とサイクル番号だけで判定しており、「実際にpush phaseへ進んだか
どうか」を見ていなかったことが原因。`Set_Addr_To=aMSP`であることを
追加の条件としてガードし修正した。

この問題は、GHDLテストベンチで複数回のCALL.L/RET.Lの呼び出し・
条件不成立ケースを連続して実行し、MSP24の最終値を厳密に検証する
テスト（`tb_phase11_call_ret_l.vhd`）を書いて初めて検出できた
（1回目・2回目のCALL.L/RET.L往復では偶然辻褄が合ってしまい、3回目で
初めて矛盾が表面化した）。

## さらに別種の制約：`MCycle`の3bit幅そのものの上限（Phase12で発覚）

上記はいずれも「`MCycle=110/111`という値の意味が重複していた」こと
による誤動作で、ガード条件の追加だけで解決できた。しかし、Phase12で
`CALL.M2 addr24`（addr24の3byteフェッチ＋4byteの戻りフレームpush、
合計で1opcode+3+4=8 MCycles必要）を設計した際、**ガードでは解決
できない、信号幅そのものの限界**に突き当たった。

`MCycle`は`std_logic_vector(2 downto 0)`（3bit）であり、表現できる
最大値は7。CALL.Lの7サイクルはこの上限ちょうどに収まったが、
CALL.M2が必要とする8サイクルは**原理的に表現不可能**で、ガード条件の
追加では対処できない。これは「潜在バグ」ではなく、**T80コアの
アーキテクチャ上のハード制約**であり、解決するには

- `MCycle`を4bit以上へ拡張する（t80_mcode.vhd全体の既存比較箇所
  （100箇所以上）に影響する大改修）、または
- CALL.M2のフレーム構成・フェッチ方式自体を見直し7 MCycle以内に
  収める代替設計

のいずれかが必要となる。当初は`CALL.M2 addr24`の実装を保留し、
制約として明記するに留めていたが、後日下記の通り**解決済み**。

### 解決（追記）：`MCycle`/`MCycles`を3bit→4bitへ拡張

ユーザーと相談のうえ、`MCycle`/`MCycles`（および関連する
`Pre_XY_F_M`/`MCycles_d`）を4bit幅へ拡張する方針を採用した。

**採用した理由**: 既存の3bitビットリテラル比較・代入（約150箇所）は
すべて「3文字のビット文字列リテラルに`"0"`を1つ追加する」という
機械的な置換で済み、かつVHDLは固定長ビット文字列の長さ不一致を
**厳密にコンパイルエラーとして検出する**ため、置換漏れが残っても
静かに動作することはなく、必ず検出できる。これは、今回発見した
MCycle=110/111無条件発火バグのような「暗黙の状態共有」に起因する
危険とは性質が異なり、安全に実行できる変更だと判断した。

**実際に機械的置換で見つかった落とし穴**: 置換は正規表現ベースの
スクリプトで行ったが、最初の置換パターンは`MCycle <= "110"`（代入）
と`MCycle = "110"`（等価比較）のみを対象としており、**`MCycle /= "001"`
のような不等価比較（`/=`演算子）を見落としていた**。この見落としは
GHDLでは警告すら出さずにコンパイルが通ってしまったが、Gowinの論理
合成ツールが`WARN (EX4196): Comparison between unequal length arrays
always returns TRUE`という警告で検出した（長さの異なる配列同士の
`/=`比較は、VHDLの言語仕様上**常にTRUEを返す**ため、意図した条件
判定が完全に無効化されてしまう——これは「コンパイルエラーで必ず
検出できる」という前提が通用しない、**静かに壊れる**危険なケース
だった）。該当2箇所（[t80.vhd](/d:/Users/HeroineFactory/Documents/GIT/MSXNano-Z80X/msxnano-24bit/fpga/G80A/t80.vhd)の16bit INC/DEC
レジスタペアwriteback条件、`IncDec_16(2)='1' and (... MCycle /= "001" ...)`）
を修正し、最終的にGHDL回帰・Gowin合成の両方で警告なしを確認した。

**教訓（今後同様の幅拡張を行う場合への申し送り）**: VHDLのビット
文字列リテラル比較を機械的に置換する際は、`=`/`<=`（代入）だけでなく
`/=`・`<`・`>`・`<=`・`>=`（比較版）**全ての演算子**を正規表現の
対象に含めること。また、**GHDLのコンパイルが通ったことは安全性の
保証にならない**——今回のように、長さ不一致の`/=`比較はGHDLでは
エラーにならず、Gowin等の論理合成ツール側で初めて警告が出るケースが
ある。幅拡張作業の最終確認には、GHDL回帰だけでなく**必ずGowin合成
（またはそれに類する厳密なVHDL処理系）も実行**し、警告ログを
確認すること。

**外部インターフェースへの配慮**: `MC`デバッグ監視用ポート（3bit、
`g80a.vhd`/`T80s.vhd`が`MCycle = "001"`という判定にのみ使用）は
互換性のため幅を変更せず、`MC <= MCycle(2 downto 0);`と下位3bitを
切り出す形に変更した。これにより、CALL.M2の8サイクル目（4bit表現で
のみ可能な値）以外は全て従来通りの値がこのポートに現れる。

**最終検証**: GHDL回帰（Phase2〜Phase12の全13テストベンチ）は幅拡張
後も全てパス。`tb_phase12_mode_control.vhd`にCALL.M2の往復テスト
（Test8/Test9）を追加し、PASS確認済み。Gowin合成もクリーン（BSRAM
使用率45/46=98%は変化なし、Logic/Registerは新命令分のみ微増）。

## 検証方法

上記5箇所の修正は、**DD/FD+CB自体の動作を一切変更していないこと**を
GHDL回帰（Phase2〜Phase12の全テストベンチ、特にDD/FD+CB経由の
(IX+d)アドレス計算を直接検証するPhase2/Phase8のテストを含む）で
確認済み。CALL.L/RET.L/CALL.M0/M1/M2/RET.M自体も、各々専用のGHDL
テストベンチ（`tb_phase11_call_ret_l.vhd`、`tb_phase12_mode_control.vhd`）
で複数回の往復・条件分岐・MSP24の正確な復元を検証済み。Gowin合成も
エラーなしを確認済み。
