# 24bit拡張メモリ: バス分離と要求受理競合の解決

記録日: 2026-10-23

対象: MSXnano-Z80X / Z80X24、Tang Nano実機

## 1. 結論

今回の調査では、24bit CPUのメモリアクセスを既存MSXシステムへ接続する部分に、
性質の異なる二つの問題を特定・修正した。

1. **アドレス空間の分離不備**:
   非ゼロバンクのアクセスが通常MSX側のデコーダにも届き、
   `01:FFFF`への書込みで拡張スロット選択レジスタを変更していた。
2. **要求とペイロードの確定順序の不備**:
   SDRAM要求だけが先行し、調停回路が更新前のアドレス・書込み種別を受理する
   タイミングがあった。

2026-10-23のユーザー実機報告で、後者の修正後は**リセット直後でもLD24MIが
安定して`PASS=13 FAIL=00`**となった。`13`は16進数であり、19判定すべての成功を表す。
実行回数・リセット回数の数値は報告されていないため、故障率の数値評価は行わない。

P24TESTは、先行するバス分離修正後にTest7を含む全13判定で
`PASS=0D FAIL=00`となった。最終の要求受理修正後にP24TESTを再実行した結果は、
この記録時点では未報告である。

これはZ80X24で得られた結果である。eZ80実装時にも設計上の教訓は利用できるが、
eZ80そのものの命令互換性や外部バスタイミングを検証した結果ではない。

## 2. 観測と切り分けの経緯

| 段階 | 観測 | 判断・対応 |
|---|---|---|
| 当初 | PUSH24/POP24の境界またぎで値不一致・停止 | CPU内のアドレス更新とWAIT制御を調査 |
| LD24MI導入 | MSP24を使わない転送でもFAIL・停止 | MSP24固有の問題とは限らない |
| テスト点検 | M1中のDOS呼出しなど、診断プログラム側にも問題 | 測定をDI/M1、表示と比較をM0に分離 |
| 停止位置特定 | `01:FFFF`書込み後のF3付近で停止 | 通常MSX側デコードへの副作用を調査 |
| バス分離後 | LD24MI旧13判定版、P24TEST全13判定がPASS | 通常MSX空間への副作用の修正効果を確認 |
| 初回アクセス調査 | 初期の記憶では`got=xxCCCC`、後には再現しないこともあった | この値だけから原因を確定しない |
| 複数パターン試験導入 | リセット直後に同じFAILを3ログで記録 | 前回の正解値による見かけのPASSを排除 |
| RTL競合再現 | 意図した書込みが古いアドレスへの読出しとして受理された | 要求とラッチ確定順序を修正 |
| 修正後 | タイミング回帰18ケースPASS、実機リセット直後も安定PASS | 今回の報告現象の解消を確認 |

過去に試したWAIT修正がすべて不要だった、または過去の全症状が単一原因だったとは
断定しない。今回の修正は既存のWAIT機構を維持し、別途確認した接続上の欠陥を直した。

## 3. 問題A: 非ゼロバンクから通常MSX空間への副作用

### 原因

通常MSX側の拡張スロット選択デコードは、下位16bitが`FFFF`であること、
メモリ書込み要求、スロット選択などで動作していた。
CPUの非ゼロバンクを遮断していなかったため、拡張メモリの`01:FFFF`への書込みも
この条件を満たした。

SDRAM調停でCPUを優先しても、独立して動作するスロット選択レジスタへの書込みは
防げない。「どのメモリを選ぶか」と「他の機器を動かさないこと」は別の要件である。

### 修正

[memory_bus_router24.v](../../fpga/src/memory_bus_router24.v)をCPUラッパ直後に配置した。

```text
CPUのアドレス・制御信号
            |
       メモリバス分離
            +-- bank00 ------> 通常MSXメモリデコーダ
            +-- bank非ゼロ --> 拡張メモリ側
I/O要求 --------------------> 従来のI/O経路
```

- CPU内部の演算・命令実装を変えず、システム側で要求を分離する。
- アドレスをゼロへ置換するのではなく、非対象側のMREQを無効にする。
- 未実装の非ゼロバンクも通常MSX側へ流さない。読出しはFFh、書込みは無効とする。
- I/O経路は維持する。
- SD有効化レジスタの書込み条件にも、分離後のMREQを要求する。

### 検証

[tb_memory_bus_router24.sv](../../fpga/G80A/test/tb_memory_bus_router24.sv)で、
256バンク×8アドレス×32制御パターンの65,536通りと追加シナリオを確認した。
境界書込み、bank00のスロット/SD書込み、VDP I/Oの維持も確認した。
実機でLD24MIの停止が解消し、P24TESTも全13判定PASSとなった。

## 4. 問題B: 要求だけが先行して古いラッチ値を受理

### 実機での確定した症状

以下の三つのログは同一結果だった。

- [RESULT.TXT](../../hardware_test/Ld24MemIndirectTest/RESULT.TXT)
- [RESULT1.TXT](../../hardware_test/Ld24MemIndirectTest/RESULT1.TXT)
- [RESULT2.TXT](../../hardware_test/Ld24MemIndirectTest/RESULT2.TXT)

```text
Test1 R/W patterns 01:9000: FAIL (got=0599AA, want=000000)
  first failing step=01
...
PASS=12 FAIL=01
```

段階1は`01:9000`〜`01:9002`へ`00 00 00`を書いて読み戻す試験である。
実測値は前回の正解値`AA 99 05`と一致していた。後続の通常LD24読出しは成功した。

なお、パターン試験は最初の不一致だけを記録するため、このログから
「段階2以降はすべて成功」とは判断できない。また、旧データが読めたことだけでは、
書込み失敗と読出し失敗のどちらかを単独で断定できない。

### RTLで再現した競合

修正前の[top.v](../../fpga/top.v)では、拡張メモリ要求を組合せ信号で直ちに出し、
その要求に対応するアドレスと書込み種別は`WS_ARMED`でラッチしていた。

一方、[memory.v](../../fpga/src/memory.v)は受理段階`3'd1`でCPU要求を優先選択し、
渡されたアドレスと書込み種別を取り込む。

```text
クロック直前:
  CPU要求 = 1
  アドレスラッチ = 更新前
  書込みラッチ = 更新前
  メモリ調停 = 受理段階

同じ立上がり:
  top側    : 新しいアドレスと書込み種別をラッチ
  memory側 : 更新前のアドレスと書込み種別を取り込む

クロック後:
  top側の値は正しいが、memory側には古い要求内容が確定済み
```

Verilogのノンブロッキング代入でも、別の同期処理が同じエッジで
更新後のレジスタ値を直ちに参照するわけではない。VHDLの信号代入で注意すべき
同一クロック内の旧値参照と同種の問題である。

リセット後のアドレスラッチは0、書込み種別は読出しだった。
再現テストでは次の不一致を確認した。

```text
意図したアクセス : address=659000 write=1
実際の受理内容   : address=000000 write=0
```

`659000`はCPUの拡張アドレス`01:9000`に、
物理SDRAM配置のベース`640000`を加えた値である。

メモリ調停が待機段階から始まる場合は、その間にtop側のラッチ更新が済むため成功した。
通常MSX側要求が先に調停を進めていた場合は、この余裕がなく競合が露出した。
単純な拡張メモリ専用モデルだけでは見逃しやすい条件である。

### 修正1: 確定済みの要求だけを公開する

```verilog
// 修正前
wire cpu_sdram_req = cpu_sdram_active;

// 修正後
wire cpu_sdram_req =
    cpu_sdram_active && (wait_state == WS_WAITING_DONE);
```

`WS_ARMED`でアドレス・書込み種別を確定し、状態遷移後に要求を公開する。
CPUのWAITはその間も維持する。完了後は`WS_IDLE`へ戻るので、
CPU側のバス信号が残っていても要求を再発行しない。

### 修正2: 未受理の要求が別アクセスの終了を妨げない

修正1の回帰試験では、通常MSX側アクセスの終了段階で未受理CPU要求を待ってしまう
停止条件も見つかった。終了判定を次に変更した。

```verilog
// memory_ctrl の終了段階 3'd4
if (mapper_req == 0 && megaram_req == 0 &&
    (cpu_sdram_req == 0 || sdram_owner_cpu == 0)) begin
    sdram_seq <= 3'd0;
end
```

終了するアクセスがCPU所有でなければ、待っているCPU要求は新規要求であり、
その要求を受理できる待機段階へ戻る必要がある。
CPU所有アクセスの終了では、従来どおり自分の要求の解除を確認する。

## 5. 検証結果と限界

| 検証 | 結果 | 分かること・限界 |
|---|---|---|
| バス分離RTL回帰 | 65,536通りと追加シナリオPASS | 通常側への要求遮断とI/O維持 |
| 要求受理RTL回帰 | 全18ケースPASS | 読出し/書込み、待機中到着、通常側受理から0〜7クロック後の到着 |
| 同回帰の完了確認 | PASS | WAIT解除と、完了後にバスが残る場合の二重発行防止 |
| COM実行回帰 | `PASS=13 FAIL=00` | 命令列、比較、表示、集計、モード/割込み管理 |
| COM読出し故障注入 | `PASS=10 FAIL=03` | 不一致と段階番号を正しく報告すること |
| Gowin論理合成 | Z80X24版・標準版とも成功 | 合成可能性。これだけでは配置配線後のタイミングを保証しない |
| 最終実機LD24MI | リセット直後も安定して`PASS=13 FAIL=00` | ユーザー報告による今回の症状の解消 |

要求受理テスト:

- [tb_cpu_sdram_request_timing.sv](../../fpga/G80A/test/tb_cpu_sdram_request_timing.sv)
- [run_cpu_sdram_request_timing.ps1](../../fpga/G80A/test/run_cpu_sdram_request_timing.ps1)

リポジトリルートで実行する。

```powershell
& .\fpga\G80A\test\run_cpu_sdram_request_timing.ps1
```

スクリプトは`top.v`の実際のWAIT/要求ブロックを抽出し、実際の`memory_ctrl`と接続する。
手書きの複製ロジックだけを検査する構成にはしていない。
ただし、抽出はソースの区切り文字に依存するため、ブロック構成を変えたときは
スクリプトも点検する。

この回帰は物理SDRAMの書込み結果や実際のCPU命令列、実際の映像クロック位相を
再現するものではない。RTL競合の再現・修正と実機改善が対応したことは強い根拠だが、
実機内部波形で3byteすべての失敗経路を直接観測したわけではない。

## 6. 実機メモリ試験から得た教訓

同じ値を書いて読むだけのテストは、前回の正解値が残っていると書込み消失を見逃す。
今回の試験では、各3byte領域へ次を順に書き、毎回読み戻して比較するようにした。

1. `00 00 00`
2. `FF FF FF`
3. `55 AA 55`
4. `AA 55 AA`
5. 最後に残す値のビット反転
6. 最後に残す値

読出し命令の試験では正解データを準備する。
書込み命令の試験では、**対象命令の実行直前に期待値の反転を残す**。
これにより対象命令の書込み自体が失われても、前回の値で偶然PASSしにくくなる。

表示・DOS呼出しはモードを戻してから行い、測定中はDIを維持する。
診断用のOS/BIOS呼出しがCPU状態や割込みを変えないかも、テスト設計の一部である。

これは対象命令と限られたアドレスを検証する試験であり、全メモリ検査ではない。
アドレス線のエイリアス、全ビットのwalking-one/zero、長時間保持、全バンクや
全負荷条件の保証には、別の試験が必要となる。

## 7. 将来のeZ80実装へ引き継ぐチェックリスト

eZ80固有のADL/短縮アドレス動作やバスタイミングは、採用する仕様・コアに従って
別途定義する。本件のbank00規則をそのままeZ80の仕様と見なしてはならない。
そのうえで、以下は共通して役立つ。

- [ ] CPUから見たアドレスと、MSX側機器が見るアドレス空間を明文化する。
- [ ] 拡張領域アクセスが互換領域の特殊レジスタへ副作用を起こさないようにする。
- [ ] データ選択だけでなく、非対象機器の要求信号を遮断する。
- [ ] 未実装領域の読出し値・書込み動作を明示し、互換領域へフォールバックしない。
- [ ] 要求の有効化より先に、アドレス・方向・データ・属性を確定する。
- [ ] 受理と完了の意味を分け、待機中・受理済み・完了済みを区別する。
- [ ] アドレス・方向・データを同一トランザクションとして扱う。
      今回の修正はアドレス/方向の順序が対象であり、書込みデータを新たに
      ラッチしたものではない。データの安定性は別途保証する必要がある。
- [ ] 完了は受理時の所有者へ返し、未受理の別要求で完了待ちを延長しない。
- [ ] WAIT解除はデータ確定後に行い、同じ要求を二重受理しない。
- [ ] リセット後の最初のアクセスと、通常領域から拡張領域への切替えを試す。
- [ ] バンク境界だけでなく、他クライアントの受理・処理・終了段階との重なりを試す。
- [ ] 理想メモリでのCPU試験と、実際のラッパ/調停RTLの試験を分けて用意する。
- [ ] 実機では初回実行・再実行・リセット・電源再投入を区別して記録する。

## 8. note記事向けの構成案

### タイトル案

**「24bit化したZ80がリセット直後だけ失敗した理由
― 命令ではなく、バスの境界と要求の順序だった」**

### 導入文案

24bit化したZ80で、バンク境界をまたぐ転送が止まる。CPU内部の桁上がりや
WAIT制御を疑っていたが、最初に見つかったのは、拡張メモリへの書込みが
MSXのスロット選択レジスタまで動かしてしまう問題だった。
それを直すとテストは通るようになった。しかし、リセット直後だけはまだ失敗する。
同じデータを書くだけでは見逃していた失敗を、ゼロ・全ビット1・反転パターンの
読み書きが見えるようにした。

### 本文の流れ

1. バンク境界の不良に見えた発端と、MSP24を使わないLD24MIでの切り分け。
2. `01:FFFF`が通常MSX側にも届いた問題。調停の優先順位では副作用を止められない。
3. バス分離で一度はPASS。それでも残った「リセット直後だけ」の失敗。
4. `got=0599AA, want=000000`が示した、前回の値に隠れるテストの弱点。
5. 同じクロックで「新しい要求」と「古いラッチ値」が組み合わさる図解。
6. 要求を確定後に公開し、所有者別に終了条件を整理した修正。
7. RTL回帰18ケースと、実機リセット直後の19判定PASS。
8. eZ80実装への教訓: 命令の正しさだけでなく、システム境界の契約を検証する。

### 記事で誇張しないための注意

- 「eZ80を修正した」ではなく「将来のeZ80実装へ活かせるZ80X24の事例」とする。
- PASS数は16進表示であり、`13`は19件と説明する。
- 過去の候補と確定した欠陥を区別し、古い仮説を最終原因として引用しない。
- 「完全無欠」「全条件保証」ではなく、確認した条件と実機結果を示す。
- FPGA内部の全失敗波形を採取した、と誤解される表現は使わない。
- 本ファイルの相対リンクはリポジトリ内用である。公開記事では公開URLへ置換し、
  ローカルパスや環境固有情報が不要に掲載されないようにする。
