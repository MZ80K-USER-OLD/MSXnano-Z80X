# M2割込みフリーズ: WAIT制御の原因とeZ80開発への教訓

記録日: 2026-10-29  
対象: MSXnano-Z80X / Z80X24、V16.1割込み試験、Tang Nano実機

## 1. 結論と実機結果

「M2で割込みがフリーズする」と見えていた今回の停止は、割込み命令だけの問題では
なかった。**メモリアクセスのない内部Mサイクルに対し、拡張SDRAMのWAITを立て、
発生しないメモリ要求を待ち続けた**ことが原因だった。

CPU本体と非同期バスラッパーはVHDLだが、今回修正した実機側の欠陥は
[top.v](../../fpga/top.v)のVerilogのWAIT状態機械にある。
「VHDLの割込み処理を修正して解決した」と記録するのは不正確である。

2026-10-29のユーザー実機報告:

| 試験 | 結果 | 追加の報告 |
|---|---|---|
| [I161TEST](../../hardware_test/V161IRQTest/README.md) | `PASS=04 FAIL=00` | `ABCDVHDVHM` |
| [H161TEST](../../hardware_test/V161HALTTest/README.md) | `PASS=03 FAIL=00` | 個別のVRAM行全文は未報告 |

I161はIM1/IM2とMSP24境界条件を組み合わせた4ケースを、
H161はM0/M1/M2で各2回のHALT割込み待ち・ハンドラ実行・復帰を検査する。
I161は割込み設定なしの有限待ち予備試験を通らないと本試験へ進まないため、
最終PASSは予備試験の完了も意味する。ただし`TM1abc2345OK`全文自体の報告はない。

これは今回の停止の解消を示す。全命令・全位相・全割込み条件での無欠陥や、
eZ80互換性を証明する結果ではない。書込み済みFPGAイメージのハッシュは
実機報告と直接照合していないため、この記録では実機使用版のハッシュを断定しない。

同日の追加実機回帰では、V161TEST、P24TEST、LD24MI、P12TEST、
I16M2、I24M2、INDEX16、INDEX24もすべて期待値どおりPASSした。
さらにSOFARUNからスペースマンボウを起動してプレイできたとのユーザー報告があり、
通常MSXソフトの代表的な動作も確認した。
詳細は[実機回帰結果一覧](../../hardware_test/README.md)を参照。
追加説明により、GowinでFPGAのSRAMへ書き込む運用で毎回電源再投入していること、
リセット後にもSOFARUNからスペースマンボウを起動してプレイできたことを確認した。
電源再投入・リセット後の動作を一律に未確認とした従来の整理は訂正する。
さらに同日、リセット直後のLD24MIで`PASS=13 FAIL=00`との報告があり、
リセット後初回の拡張メモリアクセス回帰も合格した。
その他のCOMの起動後の実行順と反復回数、プレイ時間、音源の個別確認は未記録であり、
長時間安定性や全ソフト互換性まで確認済みとは扱わない。

その後の開発側の回帰・保存記録は
[WAIT v9検証記録](../../verification_data/wait_v9_regression_20261029/README.md)に分離した。
既存の配置配線レポートにはSetup/Hold等の違反が残っており、
今回の実機機能PASSを「タイミング収束済み」の証拠にはしない。

## 2. なぜ割込みの問題に見えたのか

| 観測 | 後から判明した意味 |
|---|---|
| I161が`TM`、`TM1`、`TM1.`付近で停止 | 表示だけではIRQ、ループ、メモリWAITの区別がつかなかった |
| トレース追加後、実質`TM1abc`で停止 | 割込み設定前の有限ループでも停止し、IRQ固有という仮説を崩した |
| H161が`HALT arming M02`で停止 | M0/M1との差から、非ゼロPCバンクでの実行と外部接続を疑う根拠になった |
| CPU単体のCOMシミュレーションはPASS | CPU命令モデルだけでは実機のWAITデッドロックを再現していなかった |

ループ内のJR/DJNZにも、ハンドラ内の分岐にも、外部メモリ要求を出さない内部
Mサイクルがある。割込み受付前に止まる場合と、受付後に止まる場合を、
画面上の短い停止表示だけで同じ「割込み受付不良」にまとめてはいけなかった。

元の実機停止時の全信号波形は取得していないため、各旧版の停止位置をすべて
単一の命令に断定はしない。一方、後述のG80a統合試験では、修正なしのDJNZが
同じWAIT循環で停止することを直接確認した。

## 3. 関連するVHDLと、停止までの因果関係

### 3.1 アドレス更新はメモリ要求の宣言ではない

[t80.vhd](../../fpga/G80A/t80.vhd)は、Mサイクル終端の`T_Res`で
`update_addr`を立て、次のサイクル用アドレスを設定する。
関連部分の抜粋:

```vhdl
if T_Res = '1' then
    update_addr <= '1';
    A_Bank_r <= (others => '0');
    -- 分岐・アドレス選択の処理が続く
```

アドレス選択のPC側では、M2の`A_Bank_r`に`bank_pc_r`を使う。
したがってbank01で実行すると、内部サイクル用のアドレスにも非ゼロバンクが
現れ得る。**アドレスが有効そうに見えることと、そのサイクルがメモリを使うことは別。**

なおVHDLの信号代入は、そのプロセス内で直ちに他の信号参照へ反映されない。
同一エッジで更新するアドレスを受け手が読む場合、更新前か更新後かを時系列で
確認する必要がある。今回のWAIT制御はバンクの確定を待って読んでいたが、
「確定したバンクが非ゼロなら要求が来る」という別の誤りを残していた。

### 3.2 内部サイクルではMREQが出ない

[t80_mcode.vhd](../../fpga/G80A/t80_mcode.vhd)は、成立するJR/DJNZ等の
内部サイクルで`NoRead <= '1'`を指定する。
[g80a.vhd](../../fpga/G80A/g80a.vhd)の非M1サイクルのバス生成条件は次のとおり。

```vhdl
if TState = "001" and NoRead = '0' then
    IORQ_n_i <= not IORQ;
    MREQ <= not IORQ;
    if IORQ = '0' then
        RD <= not Write;
    elsif IORQ_n_i = '0' then
        RD <= not Write;
    end if;
end if;
```

`NoRead='1'`の内部サイクルはこの経路でメモリ要求を開始しない。
これは内部演算に外部読出しを伴わせないための動作であり、それ自体を
「VHDLの誤生成」と扱うべきではない。

### 3.3 CPUは内部サイクルでもWAITで止まる

[t80.vhd](../../fpga/G80A/t80.vhd)のTState更新には次の条件がある。

```vhdl
if TState = 2 and Wait_n = '0' then
elsif T_Res = '1' then
    -- 次のサイクルへ進む処理
```

この条件に`NoRead`の除外はない。外側からWAITを入れると内部サイクルも
TState=2に留まる。CPUを止めたまま「そのCPUが次に出すはずの要求」を待つと、
要求が存在しないケースでは両者が永久待ちになる。

### 3.4 問題だったWAIT状態機械

修正前の[top.v](../../fpga/top.v)の構造を要約すると、次のとおり。

```text
WS_IDLE:
    update_addrの新しい立上り && 拡張SDRAM範囲のバンク
        → WAITを立て、WS_ARMEDへ
WS_ARMED:
    実際のMREQとRD/WRが来た場合だけ
        → アドレス・書込み種別をラッチし、WS_WAITING_DONEへ
WS_WAITING_DONE:
    SDRAM完了通知が来たらWAITを解除
```

欠けていたのは、**WS_ARMEDで「そもそもメモリ要求のないサイクルだった」と
判明した場合の出口**である。

```text
M2、PC bank01
  → 内部サイクルにもupdate_addrとbank01が現れる
  → 外側がWAITを立てる
  → 内部サイクルなのでMREQは出ない
  → WS_ARMEDが完了待ちへ進めず、WAITも解除しない
  → CPUはTState=2から進めない
```

## 4. なぜこの設計を生成・採用したのか、何が不足していたのか

ここでの理由は、ソースのコメントと作業経緯から確認できる設計上の理由であり、
生成時の内部的な思考を推測したものではない。

### 正当だった目的: WAITを早く出す必要があった

先行するPUSH24/POP24の調査では、MREQ/RD/WRが出てからWAITを立てる方式では
間に合わない問題があった。[g80a.vhd](../../fpga/G80A/g80a.vhd)は、
同じ`CLK_n`立下り・`clk_falling`条件でバス信号の更新と
`Wait_s <= WAIT_n`のサンプリングを行う。

そのバス更新を見てから外側が反応しても、同じサンプリング時点に遡ってWAITを
見せることはできない。WAITを長く保持するだけでは、最初の観測遅れを直せない。
そこで、バス信号より早い`update_addr`を使ってWAITを先行して立てた。

また`update_addr`はクロックイネーブル間でhighを保持するため、
highレベルを毎回新要求と誤認しないエッジ検出も必要だった。

### 誤っていた前提: 先行予告を要求の確約として扱った

早期WAIT自体は必要だったが、次の二つを同一視した。

- 「次のサイクル用アドレスが更新された」
- 「次のサイクルでは必ず外部メモリ要求が来る」

非ゼロバンクのPUSH/POP・ロード等を中心に検証し、**予告はあるが要求は来ない
内部サイクル**をWAIT機械の仕様に含めなかった。安全に待たせることを優先する一方で、
待機状態から必ず抜けられるかという進行性の確認が不足していた。
これは私が採用した接続設計・検証範囲の不足であり、ユーザーの実行手順の問題ではない。

### シミュレーションPASSを過大評価した

[tb_ld24mi_com.vhd](../../fpga/G80A/test/tb_ld24mi_com.vhd)のCOM試験は、
命令処理や物理アドレス・フレームの検査には有用だが、
実機のG80a非同期ラッパーとtopのWAIT状態機械を含まない。
そこを通る試験だけで、実機接続まで正しいと判断してはいけなかった。

## 5. 今回とった対策

### 5.1 メモリ要求のないサイクルにはWAIT解除経路を設けた

[top.v](../../fpga/top.v)のWS_ARMEDに、次の処理を追加した。

```verilog
if (clk_falling_3m6_54 == 1 && wait_armed_falls != 2'd3)
    wait_armed_falls <= wait_armed_falls + 2'd1;

if (cpu_sdram_active == 1) begin
    // アドレス・書込み種別をラッチし、完了待ちへ
end
else if (wait_armed_falls == 2'd3 && extended_mreq_n == 1) begin
    cpu_sdram_wait_n <= 1;
    wait_state <= WS_IDLE;
end
```

カウンタはリセット時とWS_ARMEDへの入場時に0へ戻す。
このG80aの通常メモリサイクルでは、最初のCPU立下りでMREQが出て、
書込みのWRは次の立下りで出る。3回を数えた後もMREQが非アクティブなら、
要求のないサイクルとして解除する。非ブロッキング代入なので、
3への更新とその判定は同じクロック処理内で即時に行われるわけではない。

重要なのは、単なる「一定時間たったら強制解除」ではないこと。
MREQが出ているサイクルはこの出口で解除せず、実要求を優先し、
要求を出した後は従来どおりSDRAM完了までWAITを維持する。
NoRead等の新規ポート追加やCPU命令処理の変更は今回行っていない。

### 5.2 修正なしで失敗する統合試験を追加した

[tb_hw_m2_internal_cycle_wait.vhd](../../fpga/G80A/test/tb_hw_m2_internal_cycle_wait.vhd)は、
実際のG80aとWAIT機械のVHDLモデルを組み合わせ、bank01上のDJNZ、JR、ADD HL、
HALTからの割込み処理を実行する。SDRAMは調停待ちを含む簡略モデルである。

```powershell
.\fpga\G80A\test\run_hw_m2_internal_cycle_wait.ps1
.\fpga\G80A\test\run_hw_m2_internal_cycle_wait.ps1 -WithoutFix
.\fpga\G80A\test\run_cpu_sdram_request_timing.ps1
```

- 修正あり: PASS、内部サイクルのWAIT解除9回、ADD HL結果2468h、
  CPU内部IntCycleとハンドラ署名A5hを確認。
- `-WithoutFix`: 意図どおりFAIL。
  `WS_ARMED / WAIT=0 / A=01:0004 / MC=3 / TS=2 / IR=10`で停止。
  `IR=10h`はDJNZであり、HALTや割込み受付以前に再現する。
- 実際のtopのWAITブロックを抽出する要求タイミング試験:
  従来18件に内部サイクルと遅延WRの2件を追加し、20件PASS。

統合試験のWAIT部分は手動モデルなので、実RTLとの乖離には注意が必要。
また割込み受付はCPU内部IntCycleで確認しており、外部IORQ/M1応答波形の
独立した適合性試験ではない。実機では別途I161/H161のPASSを確認した。

### 5.3 一回の実機実行で分岐を絞れる観測点を用意した

有限待ちのDEC、判定、分岐、途中カウンタ値、完了を別々に記録した。
HALT試験では、待機直前、ハンドラ入口、フレーム記録、IRQ ACK、復帰後を分けた。
これにより「IRQが来ない」「ハンドラ内で停止」「復帰しない」を区別する。

HALT中はソフトウェアの有限タイムアウトも動かない。
割込みなしの有限ループ試験と、HALTして割込みを待つ試験は別々に必要である。

## 6. eZ80開発へ持ち込む設計・検証チェックリスト

1. **アドレスと要求を分ける。**
   アドレス更新だけで外部トランザクションの存在を確約しない。
   メモリread/write、I/O、内部演算、refresh、割込み受付、HALTの区別を仕様化する。
2. **早期WAITには取消・不要判定の出口も設計する。**
   「予告→要求→受理→完了」だけでなく「予告→要求なし→解除」を定義する。
   各待機状態が何を待ち、その事象を自分のWAITが妨げないかを確認する。
3. **同一エッジで新しい信号値が見えると仮定しない。**
   VHDLの信号代入、Verilogの非ブロッキング代入、立上り/立下り、
   クロックイネーブル、アドレス確定、WAITサンプルの順序を波形にする。
4. **3回という数値をeZ80へそのままコピーしない。**
   今回の値は現在のG80a接続に依存する。eZ80側の実際のバス仕様と実装に基づき、
   要求が現れる最遅時点、WAITで止められる時点、I/O待ちによるイネーブル停止も
   再確認する。可能なら将来の設計では明示的なサイクル種別を渡す。
5. **要求とペイロードを一組として確定させる。**
   受理側へ要求を公開する前にアドレス・データ・read/write種別を確定する。
   完了後の要求再発行や、アドレスの後追い変化も検査する。
6. **CPU単体とCPU＋外部接続を別の合格条件にする。**
   非ゼロバンクのコードで、分岐成立/不成立、DJNZ最終回、
   16/24bit内部演算、HALT/IRQ/NMI、I/O、refresh、境界またぎを試す。
   bank00だけの実行では、非ゼロPCバンクの誤WAITを見逃す。
7. **安全性と進行性を両方検査する。**
   「未完了でCPUを進めない」に加え「要求のないサイクルは永久停止しない」
   「一度の要求を二度処理しない」をアサーション・監視期限で検査する。
   正当な長時間メモリ待ちを、要求なし判定と混同しない。
8. **故障注入でテスト自身の検出能力を確認する。**
   修正を無効化すると狙った理由でFAILし、修正するとPASSすることを残す。
   単に最後まで動くテストだけでは、今回のような見落としを防げない。
9. **実機診断は想定分岐を先回りして記録する。**
   ハンドラ入口だけでなく、受付前、フレーム、ACK、復帰先も記録する。
   表示処理自体がレジスタやフラグ、タイミングを変える影響にも注意する。
10. **使用イメージと結果を結び付ける。**
    次回は書込み対象のFPGAイメージとCOMのハッシュ、RTL版、
    テスト条件・出力全文を一緒に保存する。ビルド成功と実機使用版の一致は別確認。
