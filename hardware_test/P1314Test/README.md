# Z80X24 Phase13(M2割込み)+Phase14(RST.L) 実機検証テスト (P1314T.COM)

MSXnano-Z80X ([msxnano-24bit](../..) リポジトリ、24bit CPU拡張 "Z80X24") の
**Phase14「RST拡張(RST.L)」** と **Phase13「割り込み(M2拡張)」** を、
実機(Tang Nano)またはMSXエミュレータ上のMSX-DOS(2)から起動して確認するための、
Z80アセンブリ製テストプログラムです。

同じ対象命令を検証するGHDLシミュレーション版テストベンチが
`msxnano-24bit/fpga/G80A/test/tb_rst_l.vhd`(RST.L)と
`msxnano-24bit/fpga/G80A/test/tb_phase13_m2_interrupt.vhd`(M2割込み)にあります。
本プログラムはそれを実機上で再現・補完します。

## 必要な環境

- Windows
- Z88DK (`D:\Tool\z88dk` にインストールされている想定)
- `z88dk-z80asm` / `z88dk-appmake`
- `make` (GnuWin32 make等)
- 実行環境としてZ80X24拡張済みMSXnano実機、またはMSX-DOS(2)が動くMSXエミュレータ

PowerShellで現在のターミナルだけPATHへ追加する場合:

```powershell
$env:Path += ";D:\Tool\z88dk\bin"
```

コマンドが見つかることを確認します。

```powershell
Get-Command z88dk-z80asm
Get-Command z88dk-appmake
```

## ビルド

`P1314Test` フォルダで実行します。

```powershell
make
```

`bin\p1314t.com` が生成されます。中間ファイルは `obj` と `BINZ80` フォルダに
生成されます。`make clean` で中間ファイルを削除できます。

`build.bat` は `z80asm` を直接呼び出す簡易スクリプトです(Z88DK同梱の
旧来の `z80asm` 用で、環境によっては使えない場合があります)。標準の
ビルド手順は `make` です。

## MSX上での実行

`bin\p1314t.com` をMSXまたはエミュレータのディスクイメージ(または実SDカード)
へコピーし、MSX-DOSから実行します。

```text
A>P1314T
```

実行ファイル名はMSX-DOSの8.3形式に合わせて `P1314T.COM` としています。

## テスト内容

`p1314_test.asm` は以下の7テストを順に実行し、各チェックの結果と最後に
合計PASS/FAIL数を画面へ表示します。

| # | 内容 |
|---|---|
| Test1 | `RST.L 00H` (`ED C7`)。M2モードで物理bank05h(`TARGET_BANK`)のオフセット0000hへジャンプし、専用マーカー変数(11h)が書き換わることと`RET.L`での復帰を確認する(実行マーカー方式、P12TestのTest3/6と同じ手法) |
| Test2 | `RST.L 20H` (`ED E7`)。Test1と同じ手法でbank05hのオフセット0020hを検証する |
| Test3 | `RST.L 38H` (`ED FF`)。Test1と同じ手法でbank05hのオフセット0038hを検証する |
| Test4 | `RETN.L` (`ED 8C`) スモークテスト。手動で構築した4byte frame(`PC_L`/`PC_H`/`PC_B`/`MODE`)をMSP24スクラッチ(`01:DFFCh`)へ直接書き込み、MSP24をそこへ設定した上で`RETN.L`を実行し、正しくPC24/bank_pc/mode24が復元されることを確認する |
| DIAG1 | 診断用ストレステスト(PASS/FAIL判定なし、割込み不使用)。Test5と同程度の反復回数を、割込みを一切使わず(`DI`のまま)M2モードで実行し続けるだけのテスト。Test5でフリーズする場合に、原因が「割込み」か「M2での持続的な命令実行そのもの」かを切り分けるための診断 |
| Test5 | 実機VDPフレーム割込み(垂直帰線割込み)を使い、M2のマスク可能割込み(IRQ)がIM設定に関係なく`IVR24`へ直接分岐することを実地検証する。ハンドラがVDPステータスレジスタでACKし、`IRQ_COUNT`を+1して`RETI.L`で復帰する |
| Test6 | Test5直後、`RETI.L`は`IFF1<-IFF2`を復元しないため、その後何回VDPフレーム割込みが発生しても`IRQ_COUNT`が増加しない(マスクされたまま)ことを、固定時間busy-waitで確認する |
| Test7 | 明示的に`EI`した後、`IRQ_COUNT`が実際に2へ増加する(割込みが再び受理される)ことを確認し、一連の機構が正常に動作し続けることを確認する |

全テストがPASSすれば、Phase14のRST.L(代表して3vector)と、Phase13のM2割込み
機構(実機の本物の非同期ハードウェア割込みを使った初めての実地検証)が、
仕様書([MSX_T80_24bit化_CPU仕様書_V10](../../doc/jpn/MSX_T80_24bit化_CPU仕様書_V10_2026-10-11.md))
および[AVAILABLE_INSTRUCTIONS.md](../../AVAILABLE_INSTRUCTIONS.md)
セクション11/12どおりに動作していることが実機で確認できます。

> **実機検証状況**: 実機(Tang Nano)上で実行し、**全7チェックがPASSしました
> (`PASS=07 FAIL=00`)**(2026年10月)。これにより、Phase14のRST.L(3vector
> を代表して検証)と、Phase13のM2割込み機構(実機の本物の非同期VDP
> フレーム割込みを使った初めての実地検証、`IVR24`への直接分岐・`RETI.L`
> によるIFF非復元・`EI`による再武装のいずれも含む)が、実機で正常に
> 動作することが確認できました。この過程で、Z80X24拡張とは独立した
> MSX-DOSプログラミング一般の既知の注意点(BIOS ROM直接CALL不可・BDOSの
> 暗黙EI副作用)も2件発見し、対応しています(下記「開発経緯2/3」参照)。

## 開発経緯: 実機で発見した「M2中のネストしたMSP24スタック」問題

本プログラムの開発過程で、実機テストにより以下の問題が見つかり、Test5/6/7
の実装を修正しました(GHDL側のテストベンチでは検証されていなかった組合せ
のため、ここに記録します)。

- **症状**: Test4までは実機で正常に通過するが、Test5(実際のVDPフレーム
  割込みを使ったM2 IRQテスト)で、DIAG1(割込み不使用のM2持続実行)は
  完走するにもかかわらず、Test5は30秒以上応答が無くなる(フリーズ)。
- **原因(推定)**: Phase10の仕様により、M2モード中は通常の`PUSH`/`POP`/
  `CALL`/`RET`もすべて`MSP24`を経由する(`aSP`/`IncDec_16`機構が
  `mode24_r="10"`のときMSP24へ自動的に切り替わる設計、
  [AVAILABLE_INSTRUCTIONS.md](../../AVAILABLE_INSTRUCTIONS.md)
  セクション8参照)。当初の実装では、(1) `CALL`で割込み待ちのbusy-wait
  サブルーチンを呼び出し、(2) 割込み受理自体がPhase13の専用4byte frame
  をMSP24へpushし、(3) さらに`IVR_HANDLER`内で`PUSH AF`/`POP AF`を
  使っていたため、MSP24に対して「CALLの戻りアドレス」「割込みの4byte
  frame」「ハンドラ内のPUSH AF」の3層がネストする形になっていた。この
  「M2割込みハンドラ内で通常のPUSH/POP/CALL/RETを使う」という組合せは、
  GHDL側のテストベンチ(`tb_phase13_m2_interrupt.vhd`)では一度も検証
  されておらず(そちらのハンドラは`INC (HL)`のみで完結する単純な実装)、
  実機で初めて本物の非同期割込みのタイミングで踏んだ可能性が高い。
- **対応**: 以下の2点を修正し、EIした状態で割込みを待つ区間では
  MSP24を使うスタック操作(`PUSH`/`POP`/`CALL`/`RET`)を一切行わない
  よう設計を変更した。
  1. `IVR_HANDLER`内のレジスタ退避を`PUSH AF`/`POP AF`から、スタックを
     一切使わない`EX AF,AF'`(裏レジスタへの退避)方式へ変更。
  2. Test5/6/7のbusy-waitループを、`CALL`によるサブルーチン呼出しから
     インライン展開(ループ本体を直接埋め込む形)に変更。
- **今後の課題**: この修正により実機での動作が改善するかどうかは
  未確認(本README作成時点)。もし改善する場合、「M2モードの割込み
  ハンドラ内で通常のPUSH/POP/CALL/RETを使うと、ネストしたMSP24操作に
  起因する実機限定の不具合が起きる」という、msxnano-24bitリポジトリ
  本体側で追跡すべき新しい知見となる可能性がある(現状はこのテスト
  プログラム側の回避策のみで、CPU本体側の根本原因調査・修正は未着手)。
- **GHDL側での追加検証**: 上記の「ネストしたMSP24スタック」シナリオ
  (`CALL`→割込みの4byte frame→ハンドラ内`PUSH AF`/`POP AF`→`RETI.L`→
  `RET`という4層のネスト)を、新規GHDLテストベンチ
  [tb_m2_nested_stack.vhd](../../fpga/G80A/test/tb_m2_nested_stack.vhd)
  で決定論的なタイミングで再現したところ、**全アサーションPASS**し、
  MSP24が最終的に開始値へ完全に復元されることを確認した。ただし、
  GHDLの理想化されたメモリモデルでは`WAIT_n`が常に`'1'`固定(ウェイト
  ステートが一切発生しない)であり、実機のSDRAM経由のMSP24アクセスに
  伴うウェイトステート挿入との組合せは未検証のままである。

## 実機フリーズ時の診断用チェックポイント(画面色マーカー)

Test5でフリーズが再発した場合に原因箇所を特定できるよう、BDOSメッセージ
ではなく**VDP R#7(背景色)への直接OUT**による画面色マーカーを複数箇所に
仕込んである(BDOSメッセージ表示はハングした時点より後のコードでしか
実行されないため、本当に無限ハングした場合は何も表示されず診断にならない
- 画面色は該当コードが実行された瞬間に即座に反映されるため、ハング中でも
「最後に表示されていた色」から凍結位置を目視で判別できる)。

| チェックポイント | 内容 | 判別できること |
|---|---|---|
| DIAG1(既存) | 割込み不使用でのM2持続実行 | 完走すれば、割込み自体が原因と判断できる |
| T5_ARMED(新規) | `IVR24`/VDP R#1設定(直接OUT)完了直後、`SET_M2`+`EI`の直前にBDOSメッセージ表示 | このメッセージが出ない場合、原因はTest5のセットアップより前にある |
| 心拍(heartbeat、新規) | busy-waitループの外側ループ先頭で、残りカウント(8〜1)をそのままVDP R#7へ直接OUT | ループ自体が回り続けているか(色が周期的に変わるか)、完全に止まっているかを判別 |
| IVR24到達マーカー(新規) | `IVR_HANDLER`の冒頭でマゼンタ系の色をVDP R#7へ直接OUT | 割込みが`IVR24`へ正しく分岐できているかを判別。この色で凍結していれば、割込みエントリ機構自体かハンドラ冒頭で止まっている |
| RETI.L直前マーカー(新規) | VDP ACK・カウンタ更新完了後、`RETI.L`実行直前に明るい赤系の色をVDP R#7へ直接OUT | ハンドラ本体(VDP ACK含む)が完走できているかを判別。この色で凍結していれば、`RETI.L`自体か、そこからの復帰処理で止まっている |

これらの色はVDP R#7への直接OUTのみで行われる(BIOSを一切経由しない)。
プログラム終了時に元の値(`SAVED_R7`に退避済み)へ、同じく直接OUT方式で
復元される。

## 開発経緯2: DIAG1完走後、BIOS WRTVDP呼出しでMSX-DOSへ予期せず復帰

上記の画面色マーカーを仕込んで再度実機テストしたところ、Test4→DIAG1までは
正常に表示されるが、Test5の`WRTVDP`呼出し([T5_ARMED]メッセージの直前)で
MSX-DOSのコマンドプロンプトへ突然復帰する(ハングではなくクラッシュ的な
即時終了)現象が見つかった。

- **根本原因(確定)**: **MSX-DOSのアプリケーションからは、BIOS ROM内の
  ルーチンを`CALL 0047H`のように直接呼び出すことはできない。** 正しくは
  `CALSLT`(`001CH`、MAIN ROM)を使い、スロットを指定した間接呼出しを
  行う必要がある。本プログラムの`CALL WRTVDP`(`0047H`番地への直接CALL)
  は、この規則に反していた。これがプログラム全体を通して**唯一**の
  BIOS ROM直接CALLだった(それ以前のCALLは全て本プログラム自身の
  サブルーチン(`PRINT_STR`/`CHECK_BYTE`/`COPY_TO_BANKX`)か、スロットを
  意識せず直接`CALL 5`できるよう設計されたMSX-DOSの標準APIエントリ
  ポイントであるBDOSのみであり、いずれも問題なく動作していた)ため、
  クラッシュ箇所とちょうど一致していた。
- **対応**: `WRTVDP`呼出し(および`CALSLT`経由への書き換え)は行わず、
  より単純で確実な方法として、VDP R#1(フレーム割込み許可ビット)の
  設定・復元を、診断用の画面色マーカー(R#7)と同じ**VDPコントロール
  ポート(99h)への直接OUT**方式に統一した。VDPはI/Oポート経由でアクセス
  するハードウェアであり、スロット/BIOS ROMの概念が一切関係しないため、
  この方式であれば`CALSLT`も不要で、Test5-7の実行区間全体からBIOS ROM
  への依存を完全に排除できる。
- **結果**: この修正により、実機でTest5(`VDP IRQ -> IVR24 -> RETI.L`)が
  **PASS**するようになった。本プログラムでの、実機の本物の非同期割込みを
  使ったM2 IRQ機構の初の実地検証成功である。

## 開発経緯3: Test5成功後、Test6がFAIL(BDOSのEI副作用)

Test5がPASSするようになった後、Test6(`RETI.L`はIFF1を復元しないはず、
の確認)が`FAIL (got=02, want=01)`で失敗した。

- **根本原因(確定)**: **MSX-DOSのBDOS(`CALL 5`)は、副作用として内部で
  `EI`を実行し、呼出し前の割込み禁止状態を保存・復元しない**(CP/M由来の
  MSX-DOS標準の既知の挙動)。当初の実装では、Test5の結果表示のため
  `CHECK_BYTE`(内部で`BDOS`を使用)を、Test6の観測ウィンドウが始まる
  **直前**に呼んでいた。このBDOS呼出しが暗黙的に割込みを再武装して
  しまい、Test6のbusy-wait中に(`RETI.L`のバグではなく)正当な2回目の
  割込みが実際に受理され、`IRQ_COUNT`が02hへ増加してしまっていた。
- **対応**: Test5の結果は`CHECK_BYTE`で即座に表示せず、一旦`T5_RESULT`
  変数へ退避するだけに留め、BDOSを一切呼ばずに直接Test6の観測ウィンドウ
  (busy-wait)へ進むよう再構成した。Test5/Test6両方の結果は、Test6の
  観測が完全に終わった後(=どちらの観測ウィンドウも閉じた後)にまとめて
  `CHECK_BYTE`で表示する。
- **教訓**: M2割込み関連のテストでは、`DI`/`EI`やIFF状態を跨いで
  観測したい区間の**間**にBDOS(やBIOS)呼出しを挟んではならない。
  これは今回のZ80X24拡張固有の問題ではなく、MSX-DOSプログラミング
  全般に共通する既知の注意点である。

## 本プログラムの対象範囲・既知の制約

- **RST.LのM0/M1「完全degrade」挙動は実機テストしない。** RST.Lは
  M0/M1では通常Z80 RSTとしてSP16へ16bit pushし、固定`0000h`/`0008h`/
  .../`0038h`へジャンプする仕様だが、これらの固定アドレスはMSX-DOS/
  BIOSが既に所有している零ページ(ウォームスタートベクタ、IM1割込み
  ベクタ`0038h`等)であり、実際にジャンプさせると未知のBIOS/DOSコード
  へ分岐してクラッシュ・ハングする危険がある。この挙動はGHDL側の
  `tb_rst_l.vhd`(Test4/Test5)で既に厳密に検証済みのため、実機では
  安全な**M2のみ**(物理bank05hという完全に本プログラムの管理下にある
  領域へのジャンプ)をテストする。
- **RETN.Lの`IFF1<-IFF2`復元自体は実機テストしない。** これを独立して
  検証するには本物のNMI(ノンマスカブル割込み)が必要だが、標準的な
  MSX実機にはソフトウェアから起動可能なNMIトリガが存在しない(リセット
  /一時停止ボタン等、物理操作にのみ連動)ため。Test4は`RETN.L`が
  PC24/bank_pc/mode24を正しく復元する(=`RET.M`と同じ基盤メカニズムを
  正しく共有している)ことのみを確認するスモークテストであり、IFF周り
  の挙動差分(`RETI.L`との唯一の違い)はGHDL側の
  `tb_phase13_m2_interrupt.vhd`(Test3/Test3b/Test4、`NMI_n`を直接駆動)
  で既に厳密に検証済みである。

## 安全上の注意

- **M1/M2モードでバンクレジスタを設定した状態のままBIOS/DOSコールを行うと、
  BIOS/DOS側が内部で使う`(HL)`等のアクセスまで拡張メモリへ誤ってリダイレクト
  される危険がある**ため、[MMUTest](../MMUTest)/[P12Test](../P12Test)の先例に
  厳密に従い、画面出力やBDOS呼出しは必ずM0へ戻した後に行う。
  - Test1-4は、P12Testと同じ「`DI`→M1/M2での命令本体のテスト(BDOS
    呼出しは一切行わない)→`SET_M0`→`EI`」という区間だけ拡張
    アドレッシング/M1/M2モードを使う構成。
  - Test5-7は性質上`EI`した状態でVDP割込みを待つ必要があるため、
    busy-waitループ本体はレジスタ/メモリの単純な比較のみでBDOS呼出しを
    一切含まない。**Test5のRETI.L直後からTest7で明示的に再武装するまでは
    意図的に`EI`を一切呼ばない**(Test6が「`RETI.L`はIFF1を復元しない」
    ことを検証するため)。結果の表示(`CHECK_BYTE`、内部でBDOS関数9/2を
    呼ぶ)はIFF1=0(割込みマスク中)のまま行われるが、これらは同期的な
    単純ルーチンのため問題なく動作する。
- `RST.L`で実際にジャンプする先の物理bank05h(`TARGET_BANK`)のコードは、
  本プログラム自身の(bank00hの)データ領域内に用意したテンプレートバイト列を、
  bank-aware `(HL)`書込みで1byteずつコピーしたものです。コピー先オフセット
  (`0000h`/`0020h`/`0038h`)はbank05hという、本プログラムの64KB空間や他の
  テストプログラム(P12Testの`02h`等)とも重ならない物理bankの中なので、
  本プログラム自身やBIOS/DOSの既存コードを破壊する心配はありません。
- 拡張メモリアクセスで使用する物理bankは **01h**(MSP24スタック/Test4の
  手動frame)・**05h**(RST.L M2コピー先コード)**のみ**です。これは
  `fpga/top.v` の `CPU_SDRAM_BASE`(0x640000-)経由で、既存のMemory
  Mapper(0x000000-)やMegaRAM(0x400000-)とは重ならない安全な領域
  (0x650000以降、詳細は`doc/jpn/SDRAMメモリマップ.md` 2.2章)に収まります。
- `CALL.M0`/`M1`/`M2`・`RET.M`が使うMSP24は`01:E000h`に設定します
  (P12Test/Push24Test等と同じ安全な初期値)。RST.L(M2)の3byte戻りフレーム
  pushは単一物理bank内で完結します(MSP24が`E000h`から`DFFDh`までしか
  動かず、bank境界をまたがない)ため、Push24Test README記載の「bank境界
  またぎPUSH24/POP24で実機フリーズする既知の問題」には抵触しません。
- Test5-7で使うVDPフレーム割込み(R#1 bit5=IE)は、BIOS管理のシャドウ変数
  `RG1SAV`(`0F3E0h`)から現在値を読み出し保存した上でORでIEビットだけを
  立て、BIOS標準ルーチン`WRTVDP`(`0047h`、B=値,C=レジスタ番号)経由で
  書き込みます。**プログラム終了前に必ず元の値へ復元します**(VDP自体への
  直接`OUT`は行わず、常にBIOS経由で行うことで`RG1SAV`との不整合を防ぐ)。
- IVR24ハンドラは、VDPステータスレジスタ(`IN A,(99H)`)を読んで割込み
  要因をACKします(これを行わないとVDP側の割込み要求が立ちっぱなしに
  なり、再入・ハングの恐れがある)。M2の割込みはIM/IStatusを一切参照
  しないため、IMモード自体は本プログラムでは変更しません(標準のBIOS
  初期設定のまま)。
- プログラム終了前に、必ずM0へ戻し使用したバンクレジスタ(`HL_B`)を
  0クリアし、VDP R#1も元の値へ復元してからMSX-DOSへ復帰します
  (`SAFE_RESET`参照)。本プログラムが使用するバンクレジスタは`HL_B`/
  `RST_B`のみです(`RST_B`は00hクリアまでは行いませんが、他のテストに
  影響しない独立したレジスタです)。
- Z80X24拡張が入っていない通常のMSX実機/エミュレータ上で実行すると、
  本プログラムが使う拡張opcodeは未定義命令(多くの実装ではNOP相当)として
  扱われます。この場合、全テストがFAILと表示されますが、これは異常ではなく
  「拡張機能が存在しない」ことを意味します。
