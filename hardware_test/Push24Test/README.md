# Z80X24 Phase9 PUSH24/POP24 実機検証テスト (P24TEST.COM)

MSXnano-Z80X ([msxnano-24bit](../..) リポジトリ、24bit CPU拡張 "Z80X24") の
**Phase9「PUSH24/POP24」**を、実機(Tang Nano)またはMSXエミュレータ上の
MSX-DOS(2)から起動して確認するための、Z80アセンブリ製テストプログラムです。

同じシナリオを検証するGHDLシミュレーション版テストベンチが
`msxnano-24bit/fpga/G80A/test/tb_phase9_push24_pop24.vhd` にあります。本プログラム
はそれを実機上で再現します。

## 必要な環境

- Windows
- Z88DK (`D:\Tool\z88dk` にインストールされている想定)
- `z88dk-z80asm` / `z88dk-appmake`
- `make` (GnuWin32 make等)
- 実行環境としてZ80X24拡張済みMSXnano実機、またはMSX-DOS(2)が動くMSXエミュレータ

PowerShellで現在のターミナルだけPATHへ追加する場合:

```powershell
$env:Path += ";D:\Tool\z88dk\bin"
```

コマンドが見つかることを確認します。

```powershell
Get-Command z88dk-z80asm
Get-Command z88dk-appmake
```

## ビルド

`Push24Test` フォルダで実行します。

```powershell
make
```

`bin\p24test.com` が生成されます。中間ファイルは `obj` と `BINZ80` フォルダに
生成されます。`make clean` で中間ファイルを削除できます。ビルドはこの環境で
実際に実行し、エラー・警告なくアセンブルできることを確認済みです。

`build.bat` は `z80asm` を直接呼び出す簡易スクリプトです(Z88DK同梱の
旧来の `z80asm` 用で、環境によっては使えない場合があります)。標準の
ビルド手順は `make` です。

## MSX上での実行

`bin\p24test.com` をMSXまたはエミュレータのディスクイメージ(または実SDカード)
へコピーし、MSX-DOSから実行します。

```text
A>P24TEST
```

実行ファイル名はMSX-DOSの8.3形式(ファイル名最大8文字＋拡張子3文字)に
合わせて `P24TEST.COM` としています(`PUSH24TEST` は10文字でファイル名の
8文字制限を超えるため短縮しました)。

## テスト内容

`push24_test.asm` は以下の8つのテストを順に実行し、各テストの結果と
最後に合計PASS/FAIL数を画面へ表示します。本増分で実装した6個のPUSH24/POP24系
命令(`ED C5`/`C1`/`D5`/`D1`/`E5`/`E1`)すべてを少なくとも1回ずつ実行します。

| # | 内容 |
|---|---|
| Test1 | `ED C5`/`C1` PUSH24/POP24 BC 往復試験。BC24をPUSH24→破壊→POP24した後、元の値に戻ることを確認 |
| Test2 | PUSH24 BC → POP24 DE のレジスタをまたいだ往復試験。データが実際にメモリ経由で転送されていること（単なるレジスタ別名化ではないこと）を確認 |
| Test3 | `ED D5`/`D1` PUSH24/POP24 DE 往復試験 |
| Test4 | `ED E5`/`E1` PUSH24/POP24 HL 往復試験 |
| Test5 | LIFO（後入れ先出し）順序試験。BC/DE/HLの順でPUSH24し、BC/DE/HLの順でPOP24すると、最後にPUSHしたHLの値がBCへ、DEの値がDEへ、最初にPUSHしたBCの値がHLへという「逆順」で復元されることを確認 |
| Test6 | いずれか1つのPUSH24/POP24命令の前後でF（フラグ）レジスタが変化しないことを確認（仕様上「F不変」、Z80標準のPUSH/POPと同様） |
| Test7 | **bank境界をまたぐPUSH24/POP24往復試験**（`fpga/src/memory.v`/`fpga/top.v`のWAIT状態生成機構の修正を実機検証するために復元。詳細は下記「bank境界またぎPUSH24/POP24の経緯」参照）。MSP24=02:0001hからPUSH24 HLを実行し、PUSH24はbank境界を下向きに（02:0001h→02:0000h→01:FFFFh→01:FFFEh）、続くPOP24は同じ境界を上向きに（01:FFFEh→01:FFFFh→02:0000h→02:0001h）またぐ。PUSH24直後に`(BC)`間接アドレッシング(`ED 91 SET_M1`)でメモリの中身を直接読み、PUSH24自体の書込みが正しいかをPOP24/MSP24の仕組みを経由せず確認した上で、HL24の値の往復、およびMSP24自体が`LD24 HL,MSP`（`ED 36`）で正しく02:0001hへ復帰していることも直接確認する |
| Test8 | **POP24単体でのbank境界またぎ試験**（PUSH24を経由せず、`(BC)`書込みでメモリを直接用意してからPOP24のみ実行する。Test7がPUSH24直後のPOP24という連続実行パターンに起因する問題なのか、POP24単体のbank境界またぎ自体が問題なのかを切り分けるための診断。詳細は下記「bank境界またぎPUSH24/POP24の経緯」参照） |

全テストがPASSすれば、Phase9で実装したPUSH24/POP24命令群が、仕様書
([MSX_T80_24bit化_CPU仕様書_V8](../../doc/jpn/MSX_T80_24bit化_CPU仕様書_V8_2026-10-05.md)
セクション9「Stack」)どおりに動作していることが実機で確認できます。
**Test1〜Test6(LIFO順序試験の5a/5b/5cを含む、合計8件のチェック)は
2026年10月に実機(Tang Nano)で全PASS・MSX-DOSへの正常復帰を確認済みです
(`PASS=08 FAIL=00`)。**Test7(bank境界またぎ往復、3件のチェック:
PUSH24書込みpeek/HL24往復/MSP24往復)は、**WAIT状態生成機構の第1版・
第2版いずれの修正でも、PUSH24の書込みpeekのみPASSし、残り2件は
バイト完全一致の同じ値でFAILし続けています**(詳細・根本原因調査・
各修正の内容は下記「bank境界またぎPUSH24/POP24の経緯」参照)。
**第3版の修正(`cpu_sdram_addr`/`cpu_sdram_write`のラッチ化)を適用
済みですが、実機での再検証はまだ行っていません**。
**Test8(新規追加)の実機検証も未実施**です。

**追記(2026-10-22、通常MSX/拡張メモリのバス分離RTL後)**: Test7を
`JP TEST8_ONLY`でスキップしていた版で、実機`PASS=0A FAIL=00`
(Test1〜6の8件+Test8のPOP24単体bank境界またぎ2件)を確認しました。
その後、Test7を再有効化した版も実機で`PASS=0D FAIL=00`となり、
Test7/8の境界またぎを含む全13判定が成功しました。
上記の未検証・FAIL記述は修正前の経緯です。
後続のSDRAM要求受理修正と合わせた記録は
[解決レポート](../../doc/jpn/24bit拡張メモリ_バス分離と要求受理競合_解決レポート_2026-10-23.md)
を参照してください。

## 本増分の対象範囲

Phase9で仕様上定義されている命令のうち、本プログラムが検証するのは
**BC24/DE24/HL24のPUSH24/POP24のみ**です。以下は別増分で対応予定のため、
本プログラムの対象外です。

- `DD ED E5`/`E1`, `FD ED E5`/`E1`(PUSH24/POP24 IX/IY。DD/ED二重プレフィクス
  の命令デコード拡張が必要。Phase7のLD24 HL,IX/IYと同様の理由）

詳細は[AVAILABLE_INSTRUCTIONS.md](../../AVAILABLE_INSTRUCTIONS.md)
セクション7を参照してください。

## bank境界またぎPUSH24/POP24の経緯（発見→根本原因特定→修正→再検証）

本プログラムの初版では、1回のPUSH24呼出し中に物理bankが変化する試験
(MSP24=02:0001hからPUSH24 HLを実行し、3回のデクリメントで
02:0001→02:0000→01:FFFF(bank繰り下がり)→01:FFFEとbankをまたぐシナリオ)
を含めていましたが、**実機検証でTest5c完了直後にシステムがフリーズする
現象が再現しました**(画面にバナーが再表示された後、応答不能に)。

GHDLシミュレーション(`tb_phase9_push24_pop24.vhd`)ではこの同じシナリオが
問題なくPASSしていたため、実機固有の問題と判断し、いったんこのテスト
ケースを削除して「bank境界をまたぐPUSH24/POP24を一切発生させない」構成
(本READMEのこのセクションを書いていた時点)に変更していました。

**その後の根本原因調査**で、以下が判明しました。

- 1回のPUSH24/POP24命令の中で、連続する3回のメモリアクセス(BANK/HIGH/LOW
  byte)がそれぞれ**異なる物理bank**へルーティングされる経路は、Phase3/5
  で検証済みの既存の拡張メモリアクセス(`(HL)`/`(BC)`/`(DE)`/`(IX+d)`等。
  いずれも1命令につき拡張アクセスは1回のみ)では一度も検証されていない、
  PUSH24/POP24が初めて踏んだ経路であったこと。
- 本プロジェクトのSD-RAMコントローラ(`fpga/src/memory.v`)には、拡張
  メモリアクセスに対してCPU側へWAIT状態を生成する機構が**全く存在
  しなかった**(`fpga/top.v`の`ex_bus_wait_n`は常時`1'b1`固定)。
- `memory.v`のSDRAM調停ステートマシン(`sdram_seq`)は、アイドル状態
  (`sdram_seq==3'd0`)のときしか新規リクエストの宛先(`cpu_sdram_addr`)を
  安全にラッチできない。CPU側に一切のWAIT待機機構(バックプレッシャー)が
  無いため、「コントローラが前の書込みの処理中にもかかわらず、次の
  M-cycle(PUSH24の次のbyte書込み)が既に開始してしまう」ケースでは、
  アドレス/書込みフラグの取りこぼし・意図しない領域の破壊が起こり得る
  という設計上の欠落が、根本原因と判断されました。

**修正**: `fpga/src/memory.v`の`memory_ctrl`に新規出力`cpu_sdram_busy`を
追加し(SDRAM調停ステートマシンがアドレス/書込みフラグを安全にラッチし
終えるまでアサート)、`fpga/top.v`でこれを基にした`cpu_sdram_wait_n`を
生成してCPUの`WAIT_n`入力へAND結合しました(このコードベースに既存の
`flash_wait_n`と同じ設計パターン)。これにより、bank境界をまたぐ連続
アクセス中は、SDRAMコントローラが安全にラッチし終えるまでCPUが待機
するようになります。

**再検証**: 本修正の実機検証のため、削除していたbank境界またぎシナリオ
を**Test7として復元**しました(上記テスト内容参照)。GHDL側のCPUコア
(`fpga/G80A/`配下)は今回の修正で一切変更していないため、GHDL回帰には
影響ありません。Test7がPASSすれば、本修正が実機で機能していることが
確認できます。

**追記(再検証の結果: 第1版の修正では解消しなかった)**: 上記の
`cpu_sdram_busy`/`cpu_sdram_wait_n`修正を適用したビットストリームを実機
へ書き込み、Test7を実行したところ、**Test6まで画面表示された後、同じく
フリーズする現象が再現しました**。この修正単体では本問題は解消して
いません。

再調査の結果、WAIT状態生成の設計そのものに次の問題がある可能性が高いと
判明しました。

- CPU本体(`fpga/G80A/t80.vhd`)の`WAIT_n`入力は、各M-cycleの**T2の
  タイミングで1回だけ**サンプリングされる(以後Wait_nが解除されるまで
  T2に留まる、という通常のZ80のTw挿入動作そのものだが、サンプリングの
  起点となるT2進入のタイミングが極めて限定的)。
- 一方、CPU側の制御信号`MREQ_n`/`RD_n`/`WR_n`は`t80.vhd`自身ではなく、
  別のラッパーエンティティ`fpga/G80A/g80a.vhd`が、`t80.vhd`とは異なる
  クロックエッジ(立下りエッジ、`clk_falling`ゲート)で生成している。
  これに対し、物理bank情報(`A_Bank`→`mmu_physical_bank`)は`g80a.vhd`を
  素通り(追加の遅延なし)するため、`WR_n`/`MREQ_n`より**明らかに早く**
  外部から見えるようになる。
- 第1版の修正は`cpu_sdram_req`(`bus_wr_n`/`bus_rd_n`に依存して発生)の
  立上りをトリガにしていたが、この信号が実際に見えるタイミングと、
  CPU本体がT2のWait_nを評価するタイミングとの間に、静的なコード解析
  だけでは断定しきれない微妙な競合が残っている可能性がある。

この種のサブT-stateレベルのタイミング問題は、波形を実際に観測しないと
確定的な原因特定が困難なため、**まずTest7のどの命令の実行中にフリーズ
しているかを切り分けるための診断マーカーを追加しました**。
VDPのR#7(背景色)へ、`PUSH24 HL`実行前後・`POP24 HL`実行前後・
`LD24 HL,MSP`実行後のそれぞれで異なる色を直接OUTし(P1314Testの心拍
マーカーと同じ方式)、画面が完全に応答不能になっても「最後にどの色まで
表示されていたか」からフリーズ箇所を特定できるようにしています。

| マーカー色 | タイミング |
|---|---|
| 1 | MSP24=02:0001h設定完了直後(PUSH24実行前) |
| 2 | `PUSH24 HL`(bank境界またぎ、下向き)実行直後 |
| 3 | PUSH24が書いたメモリの直接peek(`SET_M1`+`(BC)`)完了直後 |
| 4 | `POP24 HL`(bank境界またぎ、上向き)実行直後 |
| 5 | `LD24 HL,MSP`(`ED 36`)実行直後 |
| (元の色に復元) | Test7の3件のCHECK24_IX完了後 |

**追記2(診断マーカー適用後の再検証結果: フリーズが解消し、値の不一致に
症状が変化した)**: 診断マーカー(CALL/RETによる余分な遅延)を仕込んだ
状態で実機検証したところ、**フリーズは発生せず、Test7は完走するように
なりました**が、2件とも値が一致せずFAILしました
(`PASS=08 FAIL=02`、`PUSH24/POP24 FAIL(got=050A25, want=0599AA)`、
`MSP24 FAIL(got=01FFFE, want=020001)`)。

この結果は非常に示唆的です。

- `got`のBANKバイト(`05h`)はPUSH24で積んだ値と一致しており、POP24が
  bank02hのBANKバイトまでは正しく読めていることを示唆する一方、
  HIGH/LOWバイト(`0A25h`、期待`99AAh`)は一致しません。
- MSP24自体は、POP24完了後も`01:FFFEh`(=PUSH24完了直後の値、つまり
  POP24による3回のインクリメントが**一切反映されていないかのような
  値**)のまま止まっています。

`fpga/G80A/t80.vhd`のPUSH24/POP24実装を調査した結果、MSP24の加減算
(`Addr24_Dec`/`Addr24_Inc`によるbank borrow/carryを含む)は、**各M-cycle
ごとに`TState = 2 and Wait_n = '1'`が成立した、まさにその瞬間にコミット
される**設計であることが分かりました(POP24は`MCycle = 2, 3, 4`それぞれの
T2でこの条件が1回ずつ成立する必要があり、3回とも成立して初めてMSP24が
正しく02:0001hまで戻ります)。

つまりこの箇所は、**WAIT状態(Tw)の有無そのものを許容する設計ではある
ものの、挿入されたWait_nの「解除」タイミングが、CPU本体がMSP24コミットの
条件として期待する`TState=2`のタイミングと正確に一致していないと、
コミットが一部スキップされる**、という性質を持っています。第1版の
WAIT修正(`cpu_sdram_wait_n`)が、この一致を保証できていない可能性が高いと
考えられます。

これを受けて、**PUSH24自体の書込みが正しいかどうかを、POP24/MSP24の
仕組みを経由せず直接確認する診断(マーカー3)を追加しました**。
`ED 91`(`SET_M1`、データアクセスのみ24bit拡張アドレッシング)を使い、
`(BC)`register-indirect読出しでPUSH24が書いたはずの3byte
(01:FFFEh=AAh、01:FFFFh=99h、02:0000h=05h)を直接読んで比較します。
これにより、「PUSH24の書込み自体は正しいが、POP24の読出し/MSP24追跡の
方に問題がある」のか、「そもそもPUSH24の書込み自体が既に壊れている」
のかを切り分けられます。

**追記3(peek診断の結果: PUSH24の書込み自体は正しい。真の根本原因を
特定し、第2版の修正を実装)**: peek診断を仕込んで再度実機検証したところ、
**`PASS=09`(peekチェックがPASSに加算)、PUSH24/POP24本体とMSP24の2件は
引き続きFAIL**という結果が得られました
(`PUSH24/POP24 FAIL(got=0502A6, want=0599AA)`、
`MSP24 FAIL(got=01FFFE, want=020001)`)。

これにより、**PUSH24の書込み自体は完全に正しい**ことが確定し、問題は
POP24の読出し側(とそれに伴うMSP24の追跡)に完全に絞り込まれました。
さらに、HL24のBANKバイト(`got`の先頭`05h`)はPOP24の最後の読出し
(M-cycle 4、02:0000h番地)で正しく取得できている一方、HIGH/LOWバイト
(M-cycle 2/3、01:FFFEh/01:FFFFh番地)は不一致という非対称なパターンも
得られました。

`fpga/src/memory.v`のSDRAM調停ステートマシン(`sdram_seq`)を改めて精査した
結果、**第1版の修正の設計そのものに欠陥がある**ことが判明しました。

- 第1版の`cpu_sdram_busy`は、`sdram_seq`が**アドレス/書込みフラグを
  ラッチし終えた直後(state0→state1)**で解除されるよう設計されていました。
- しかし、実際に読み出したデータが`cpu_sdram_dout`へ反映されるのは、
  その**ずっと後のstate3**です(stateの間には、VDPとの帯域調停待ち
  (state2、`video_dlclk`/`video_dhclk`待ち)や実際のSDRAM読出し
  コマンド発行が挟まるため、state1→state3には数サイクル〜十数サイクル
  の遅延があり得ます)。
- 第1版の修正は、CPUを「アドレスが安全にラッチされた瞬間」に解放して
  しまうため、**読み出しデータがまだ確定していないうちにCPU側のWAIT_n
  が解除され、T80コアがその時点で`cpu_sdram_dout`に乗っていた(前の
  アクセスの)古いデータをそのまま読み取ってしまう**という欠陥を
  抱えていました。
- 加えて、`sdram_seq`はstate0(アイドル)からしか新規リクエストを
  受け付けないため、CPUが早期に解放されて次のM-cycle(異なるアドレス)
  へ進んでしまうと、その新しいリクエストはコントローラがstate4まで
  一巡してアイドルへ戻るまで**全く認識されない**可能性もあります。
- 書込み(PUSH24)側がこの欠陥の影響を受けなかったのは、書込みデータ
  (`cpu_dout`経由)自体はCPU側が既に安定して出力しているため、アドレス/
  書込みフラグさえ正しくラッチされれば(第1版の修正済みの範囲)、実際の
  SDRAM書込みコマンドが後から非同期的に実行されても結果的に正しく
  書き込めていた、という理由によるものと考えられます。

**第2版の修正**: `cpu_sdram_busy`を、**読み出しデータが実際に
`cpu_sdram_dout`へ確定するstate3まで**保持するよう拡張しました
(`sdram_owner_cpu`という新しいラッチ信号で「現在処理中のアクセスが
cpu_sdram_req由来かどうか」を記憶し、state2/state3でもbusyを維持、
state3で`cpu_sdram_dout<=RamDbi`する**その同じクロックエッジ**でbusyを
解除)。`fpga/top.v`側の`cpu_sdram_wait_n`生成ロジック自体(busyの
assert→deassertの往復を検出してCPUを解放する、という設計)は変更不要で、
busyの持続期間が正しく拡張されたことでそのまま機能するようになります。

Gowin合成・配置配線(Place & Route)は完了し、ビットストリーム生成まで
正常に確認済みです。GHDL側のCPUコア(`fpga/G80A/`配下)は一切変更して
いないため、GHDL回帰には影響ありません。

**追記4(第2版の修正の再検証結果: 全く同じ値でFAILし、効果なし)**:
第2版の修正を適用したビットストリームを実機へ新規生成・書き込みし直して
再実行したところ、**第1版と1byteも違わずバイト完全一致の同じ値で
FAILしました**
(`PUSH24/POP24 FAIL(got=0502A6, want=0599AA)`、
`MSP24 FAIL(got=01FFFE, want=020001)`、`PASS=09 FAIL=02`)。

この「修正の有無に関係なく全く同じ値になる」という結果は、第2版の
修正が想定していた「`cpu_sdram_busy`の解除が早すぎる」という仮説が
機能的に無効化されている(＝WAIT自体がそもそも機能していない、または
原因が別の層にある)ことを強く示唆しています。これを切り分けるため、
**Test8を追加しました**: PUSH24を一切使わず、`(BC)`register-indirect
書込み(peekと同じ`SET_M1`経路)で対象の3byte(01:FFFEh=AAh、
01:FFFFh=99h、02:0000h=05h)を直接メモリへ用意し、`LD24 MSP,HL`で
MSP24を01:FFFEhへ直接設定した上で、POP24 HL**単体**を実行する。
Test7は「PUSH24に引き続きPOP24を実行する」という連続パターンだったため、
もしPUSH24→POP24の連続実行自体(SDRAMコントローラの残留状態など)が
原因であれば、POP24単体のTest8では問題が再現しない可能性がある。逆に
Test8もTest7と同じ(あるいは類似の)値でFAILする場合、「POP24がbank
境界をまたいで読み出すこと自体」に根本原因があり、直前の命令列とは
無関係であることが確定する。**Test8の実機検証はまだです**。

**追記5(第3版の修正: `cpu_sdram_addr`/`cpu_sdram_write`のラッチ化、
未検証)**: 第1版・第2版がいずれも「`cpu_sdram_busy`(解除タイミング)」
側の仮説に基づく修正だったのに対し、**両者で完全に同一バイトのFAIL値が
出た**という事実そのものが、解除タイミングを変えても結果が一切変わらない
=根本原因が解除側ではなく別の層にあることを強く示唆していたため、
`fpga/top.v`の静的コードレビューにより**アサート(ラッチ)側の設計欠陥**
を新たに特定し、修正しました。

- これまでの`cpu_sdram_addr`/`cpu_sdram_write`は、`mmu_physical_bank`
  (=`A_Bank`。CPUコアの`CEN`ゲートで更新される生信号)と`bus_addr`/
  `bus_wr_n`から**毎クロック再計算される組合せ信号**であり、
  `memory_ctrl`の`sdram_seq`アービトレーションステートマシンへ直接
  供給されていた。
- `sdram_seq`がこのアドレス/書込みフラグを実際にラッチする
  (state0→state1)タイミングは、VDPとの帯域調停待ち
  (`video_dlclk`/`video_dhclk`)により、アクセス開始から数クロック
  遅れることがある(`memory.v`の既存コメント自身が
  「the live cpu_sdram_req wire could ALREADY reflect a *different*,
  not-yet-admitted access」と指摘している、まさにそのクラスの問題)。
- `WAIT_n`によってCPU全体が待機させられていても、`mmu_physical_bank`
  自体がその待機中に**本当に不変であり続ける保証はない**
  (`g80a.vhd`の`WR_n_i`/`RD_n_i`生成・外部`WAIT_n`→コア内部`Wait_n`
  同期(`Wait_s <= WAIT_n`)が`CLK_n`の立下りエッジ・`clk_falling`
  ゲートという、コア本体の`TState`更新(`CLK_n`立上りエッジ・`CEN`
  ゲート)とは異なる位相で行われているため)。
- 結果として、`sdram_seq`が実際にラッチするクロックエッジにおいて、
  組合せの`cpu_sdram_addr`が**このアクセス開始時点の値のまま安定している
  保証がない**という、解除タイミングとは独立したレース条件が存在していた。
  PUSH24/POP24だけがこれを顕在化させるのは、1命令内で3つの異なる物理
  bankへ、M-cycle間のアイドル時間がほぼゼロの状態で連続アクセスする、
  唯一の既存命令パターンだからだと考えられる。

**修正**: `cpu_sdram_addr`/`cpu_sdram_write`を組合せ信号から、
**`cpu_sdram_req`の立上りエッジ(このアクセスが最初に認識された、まさに
その`clk_54m`エッジ。既存のWAIT生成ロジックが`cpu_sdram_wait_n`を
落とすのと同じエッジ)で1回だけラッチする**方式に変更した
(`cpu_sdram_addr_r`/`cpu_sdram_write_r`)。これにより、`sdram_seq`が
実際にラッチするタイミングが何クロック遅れようと、またその遅延中に
`mmu_physical_bank`が(どんな理由であれ)変化しようと、このアクセスに
使われるアドレス/書込みフラグは常にアクセス開始時点の値に固定される。

この修正は`fpga/G80A/`配下(GHDL検証対象のCPUコア本体)には一切触れて
いないため、GHDL回帰には影響しない。**本修正はコードレビューのみに
基づくものであり、実機(Tang Nano)での合成・書き込み・Test7/Test8
再実行による検証はまだ行っていない**。次回の実機検証で、Test7/Test8の
FAIL値が変化する(特に解消する)かどうかを確認する必要がある。

**追記6(第3版修正の実機再検証結果: 全く同じ値でFAILし、効果なし。
第4版の修正として`memory.v`側の実際のバグを特定)**: 第3版の修正
(`cpu_sdram_addr`/`cpu_sdram_write`のラッチ化)を適用したビットストリーム
を実機へ合成・書き込みし直して再実行したところ、**第1版・第2版と
1byteも違わずバイト完全一致の同じ値でFAILしました**
(`PUSH24/POP24 FAIL(got=0502A6, want=0599AA)`、
`MSP24 FAIL(got=01FFFE, want=020001)`、`PASS=09 FAIL=02`)。

第1版・第2版・第3版という、根本原理の異なる3つの修正すべてが
**1byteも変化しないまったく同一の結果**になったという事実は、
これらが対象としていた「`fpga/top.v`側のWAIT生成/アドレスラッチ
タイミング」という層そのものが、実は今回のバグの原因ではなかった
ことを強く示唆していた。これを受けて調査範囲を`fpga/src/memory.v`の
`sdram_seq`アービトレーションステートマシン自体に広げたところ、
**明確な実装不整合(バグ)**を発見した。

- `sdram_owner_cpu`(第2版の修正で新設)は、その宣言コメント自身が
  「`sdram_seq`のstate3'd1でこのアクセスの所有者を一度だけラッチし、
  以後は(生の`cpu_sdram_req`/`mapper_req`を)再サンプルしてはならない
  (アービトレーション待ちで数クロック経過する間に、別のクライアントの
  要求が入れ替わっている可能性があるため)」という設計意図を明記して
  いた。
- ところが、`cpu_sdram_dout`/`mapper_dout`/`megaram_dout`のどれへ
  読み出したデータ(`RamDbi`)を書き込むかを決定するstate3'd3の
  振り分けロジックだけが、この設計意図に反して**生の`cpu_sdram_req`/
  `mapper_req`を再サンプルしたまま**になっていた(`sdram_owner_cpu`は
  `cpu_sdram_busy`の保持延長にしか使われておらず、肝心のデータ振り分け
  には未適用だった)。
- state3'd1→3'd3の間(state3'd2でVDPとの帯域調停待ちが数クロック〜
  発生しうる)に、CPU側のM-cycle境界(WAIT解除の微妙なタイミング等)に
  起因して`cpu_sdram_req`/`mapper_req`の生信号が一瞬でも入れ替わると、
  state3'd3はこの入れ替わった(=このアクセスの本来の所有者ではない)
  値に基づいて`RamDbi`を**誤った宛先レジスタ**へ書き込んでしまう。
  本来の宛先(例:`cpu_sdram_dout`)は更新されずに**前回アクセス時の
  古い値を保持したまま**になる。これはまさに、第1版〜第3版のどの
  WAIT/ラッチタイミング修正を適用しても一切変化しない、デター
  ミニスティックな「決まったbyteが読めない」症状と整合する。

**第4版の修正**: state3'd1で`sdram_owner_cpu`に加えて`sdram_owner_mapper`
も同時にラッチし(cpu/mapper/megaramの3者を区別可能にする)、
state3'd3のデータ振り分けを、生の`cpu_sdram_req`/`mapper_req`では
なく、この**ラッチ済みの`sdram_owner_cpu`/`sdram_owner_mapper`**に
基づいて行うよう修正した。

この修正は`fpga/G80A/`配下(GHDL検証対象のCPUコア本体)には一切触れて
おらず、GHDL回帰には影響しない。Gowinヘッドレス合成(`gw_sh`)で
エラーなく合成できることを確認済み。**実機(Tang Nano)での合成・
書き込み・Test7/Test8再実行による検証はまだ行っていない**。

**追記7(真の根本原因の特定と第4版の修正: GHDL上の専用再現テスト
ベンチで確認、実機検証はまだ)**: 第3版までの修正がすべて「全く同じ値
でFAIL」という結果になった後、実際の非同期ラッパー(`fpga/G80A/g80a.vhd`)
とWAIT生成チェーンを1行単位で忠実に再現する新規GHDLテストベンチ
(`fpga/G80A/test/tb_hw_push24_bank_boundary_timing.vhd`)を作成し、
サイクル単位のトレースによって**真の根本原因**を特定した。

`g80a.vhd`は、新規M-cycleの`MREQ_n`/`RD_n`/`WR_n`アサートと、
`WAIT_n`を内部`Wait_s`へサンプリングする処理を、**全く同一の
`clk_falling`エッジ**で実行している。`cpu_sdram_wait_n`はこれらの
バス信号がアサートされてから反応するため、同じエッジ内で`Wait_s`に
観測されることは通常の同期回路の因果律上**構造的に不可能**であり、
第1〜3版がどれだけWAITの保持時間や解除タイミングを調整しても、この
特定のM-cycleに関しては原理的にWAITが見逃され続けていた。

この制約を回避するため、T80コア自身が各M-cycleの`T_Res`で発火する
`update_addr`出力(次のM-cycleの`A_Bank_r`/`mmu_physical_bank`が
設定される、まさにその瞬間の信号)を使い、実際のバス信号が立つ
**前**にWAITを先行アサートする設計(第4版)に変更した。あわせて、
`cpu_sdram_busy`が「pendingなだけ(未admit)」の状態でも`'1'`を示し
解除判定が時期尚早に満たされてしまうという別のバグも発見し、
`fpga/src/memory.v`に新規出力`cpu_sdram_done`(データ確定の瞬間のみ
の曖昧さのないパルス)を追加して対応した。開発途中で発見した2つの
新たなデッドロック(偽の即座再アーム問題)も、`update_addr`に対する
真の2段階エッジ検出の導入で解消し、**これまで再現していた24通りの
パラメータ組合せすべてでGHDL上の再現が解消したことを確認済み**。

詳細な調査過程は[doc/jpn/PUSH24_POP24_bank境界またぎバグ_調査レポート.md](../../doc/jpn/PUSH24_POP24_bank境界またぎバグ_調査レポート.md)
「追記3」「追記4」を参照。Gowinヘッドレス合成でもエラーなく通る
ことを確認済みだが、**実機(Tang Nano)での合成・書き込み・Test7/
Test8再実行による検証はまだ行っていない**。また、本テストベンチの
範囲では内部MSP24レジスタは常に正しく復元されており、実機で観測
されているMSP24固着症状は今回特定した根本原因とは別のメカニズムに
よる可能性が高いため、**第4版の修正でHL24データ破損は解消しても、
MSP24固着は解消しない可能性がある**ことに注意。

## 安全上の注意

- PUSH24/POP24はMSP24(`ED35`/`ED36`で読み書きするPhase7由来の専用24bitポインタ)
  を使用し、通常のZ80 16bit SP(MSX-DOS/BIOSが使うスタック)とは完全に独立
  しています。そのためBDOS呼出しやMSX標準の割り込み処理が、MSP24や
  PUSH24/POP24で書き込んだ拡張メモリへ誤って触れる心配はなく、[MMUTest](../MMUTest)
  のようなDI/EI・モード切替は一切不要です(mode24設定にも依存せず、CPU仕様書V8
  のとおりM0/M1/M2いずれでも常時full 24bitで動作します)。
- 本プログラムが使用する物理bankは **01h, 02h, 03h, 04h, 05h のみ**です。これは
  `fpga/top.v` の `CPU_SDRAM_BASE`(0x640000)経由で、既存のMemory Mapper
  (0x000000-)やMegaRAM(0x400000-)とは重ならない安全な領域
  (0x650000-0x7FFFFF、詳細は `doc/jpn/SDRAMメモリマップ.md` 2.2章)に
  収まります。Test7のbank境界またぎ試験は意図的にbank01h/02hの組だけを
  使い、bank00h(実行中のプログラム自身の64KB空間そのもの)を経由しない
  よう設計しています。
- プログラム終了前に、使用したBC/DE/HLバンクレジスタを0クリアしてから
  MSX-DOSへ復帰します(`SAFE_RESET`)。MSP24自体は[LD24Test](../LD24Test)
  と同様、他のMSX-DOS/BIOSコードが参照することのない専用レジスタなので
  明示的なクリアは行いません。
- Z80X24拡張が入っていない通常のMSX実機/エミュレータ上で実行すると、
  `ED 04/0C/14/1C/24/2C` や `ED 35/36/C5/C1/D5/D1/E5/E1` は未定義命令
  (多くの実装ではNOP相当)として扱われます。この場合、全テストがFAILと
  表示されますが、これは異常ではなく「拡張機能が存在しない」ことを
  意味します。
